## 2. Arquitetura em camadas

O percurso de uma requisição HTTP na aplicação:

```
Requisição HTTP
      ↓
┌─────────────────────┐
│     Controller      │  rota, JSON, status code
│  (@RestController)  │  NÃO tem regra de negócio
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│      Service        │  regras de negócio, transações
│     (@Service)      │  NÃO conhece HTTP
└──────────┬──────────┘
           ↓
┌─────────────────────┐
│     Repository      │  SQL, talking with o banco
│ (JpaRepository)     │  NÃO conhece regra de negócio
└──────────┬──────────┘
           ↓
        Banco (H2)
```

**Regra de ouro adotada nesta jornada:**

> Cada camada conhece apenas a camada de baixo. A **entidade JPA nunca atravessa a
> fronteira do Service** — o que sai dele é sempre um DTO.

Isso não é "estilo". Foi o que evitou o `LazyInitializationException` e o
`StackOverflowError` documentados na [Etapa 3](#6-etapa-3--dto-e-mapper).

## 3. Etapa 0 — Setup inicial

### `application.properties`

```properties
# Banco H2 em memória
spring.datasource.url=jdbc:h2:mem:ninjasdb
spring.datasource.driver-class-name=org.h2.Driver
spring.datasource.username=sa
spring.datasource.password=

# Configuração do JPA / Hibernate
spring.jpa.hibernate.ddl-auto=update
spring.jpa.show-sql=true
spring.jpa.open-in-view=false

# Console web do H2
spring.h2.console.enabled=true
spring.h2.console.path=/h2-console
```

**Configurações que importam:**

| Propriedade | Efeito |
|---|---|
| `ddl-auto=update` | Hibernate cria/atualiza as tabelas a partir das entidades no startup. `create` recria do zero; `validate` só confere. |
| `show-sql=true` | Loga o SQL gerado — essencial para aprender. |
| `open-in-view=false` | **Fecha a sessão do Hibernate quando a requisição termina**, em vez de segurá-la até a serialização. Boa prática (evita queries N+1 silenciosas econnections ociosas), mas muda o comportamento dos erros de serialização. |

### O DDL gerado

```sql
create table tb_cadastro (
  id bigint generated by default as identity,
  email varchar(255),
  idade integer not null,
  nome varchar(255),
  missoes_id bigint,          -- chave estrangeira
  primary key (id)
)

create table tb_missoes (
  id bigint generated by default as identity,
  dificuldade_missao varchar(255),
  nome_da_missao varchar(255),
  primary key (id)
)

alter table tb_cadastro add constraint FKefsdhx90...
  foreign key (missoes_id) references tb_missoes
```

Observações:

- `nomeDaMissao` → `nome_da_missao`: o Hibernate aplica a *naming strategy* do Spring
  (camelCase no Java → snake_case no SQL). Não precisa renomear nada no Java.
- `missoes_id` veio do `@JoinColumn(name = "missoes_id")`.
- `@GeneratedValue(strategy = GenerationType.IDENTITY)` → `generated by default as identity`
  (auto-increment).

## 4. Etapa 1 — Repository

### O que é

Camada que fala com o banco. E o melhor: **o Spring Data JPA escreve 95% dela para você.**

### O código

```java
package com.example.demo.Ninjas;

import org.springframework.data.jpa.repository.JpaRepository;

public interface NinjaRepository extends JpaRepository<NinjaModel, Long> {
}
```

Quatro coisas a reter:

**a) É uma interface, não uma classe.** O corpo fica vazio porque os métodos já existem.

**b) `JpaRepository<T, ID>`** — `T` é a entidade, `ID` é o tipo da chave primária
(aqui `Long`, que casa com o `@Id` da entidade).

**c) A "mágica" do Spring Data.** No startup:

1. O **component scan** varre `com.example.demo` e subpacotes (ancorado no
   `@SpringBootApplication`), e encontra a interface
2. O Spring Data JPA **gera a implementação em tempo de execução** (JDK Proxy dinâmico)
3. Quando alguém pede `NinjaRepository` para injeção, o container entrega esse proxy
4. Ao chamar `findAll()`, o proxy intercepta e monta/executa o SQL

**d) Os métodos herdados:**

| Método | O que faz |
|---|---|
| `save(ninja)` | INSERT se `id == null`, UPDATE se `id != null` |
| `findAll()` | Todos os registros |
| `findById(id)` | `Optional<T>` — **nunca `null`** |
| `deleteById(id)` | Remove |
| `count()` | Quantidade |

> O proxy funciona porque os métodos do `JpaRepository` são de **interface**. Para
> lógica customizada dentro da interface, existem os métodos `default` e as queries
> por anotação (`@Query`).

### Validação

`./mvnw compile` → BUILD SUCCESS. App sobe sem erros: se a interface estivesse errada
(entidade incompatível, pacote fora do scan), o container morreria no startup.

## 5. Etapa 2 — Service

### O que é

Camada de **regras de negócio**. É a única que sabe o que é "um ninja válido" e o que
significa "ninja não encontrado".

### Conceito 1 — `@Service` e IoC

```java
@Service
public class NinjaService {
```

`@Service` é um **estereótipo**: idêntico a `@Component`, mas com significado semântico.
O `@ComponentScan` cria a instância e a guarda no container. Isso é **IoC
(Inversion of Control)** — você não faz `new NinjaService(...)`, o Spring faz.

### Conceito 2 — Injeção por construtor

```java
private final NinjaRepository ninjaRepository;
private final MissoesRepository missoesRepository;

public NinjaService(NinjaRepository ninjaRepository, MissoesRepository missoesRepository) {
    this.ninjaRepository = ninjaRepository;
    this.missoesRepository = missoesRepository;
}
```

**Por que construtor e não campo?**

```java
// ❌ estilo antigo — injeta no campo
@Autowired
private NinjaRepository ninjaRepository;
```

Com injeção por campo, o objeto **nasce incompleto**: existe um instante entre
`new NinjaService()` e a injeção em que a dependência é `null`. Com injeção por
construtor, o objeto só existe depois de pronto.

**Por que `final`?** Impede reassignment da dependência depois da construção. É o `final`
que torna o objeto imutável quanto às suas dependências.

**Por que não tem `@Autowired`?** Desde o Spring 4.3, um construtor único é usado
automaticamente. Só precisaria da anotação se houvesse **mais de um** construtor.

### Conceito 3 — `Optional` e `orElseThrow`

O padrão mais importante do arquivo:

```java
private NinjaModel buscarPorIdOuFalhar(Long id) {
    return ninjaRepository.findById(id)
            .orElseThrow(() -> new NinjaNotFoundException(
                    "Ninja com id " + id + " não encontrado"));
}
```

**O problema que resolve:** `findById` pode não achar nada. Se devolvesse `null`, você
teria `NullPointerException` em algum lugar imprevisível — e a exceção apareceria longe
da causa real.

`Optional` força você a **decidir** o que fazer quando não encontra:

- `.orElseThrow(...)` → "não achou" é **erro** → exceção de domínio
- `.orElse(default)` → "não achou" é **resposta válida** → valor padrão

> `orElseThrow` com **lambda** `() -> new ...` (e não `new ...` direto): a exceção só é
> *construída* se realmente for preciso lançar. Com `new` direto, o objeto seria criado
> sempre, mesmo no caminho feliz.

### Conceito 4 — `save()` decide INSERT ou UPDATE

| Situação | O que o Hibernate faz |
|---|---|
| `ninja.getId() == null` | INSERT (e preenche o id com o valor gerado) |
| `ninja.getId() != null` | UPDATE (`WHERE id = ?`) |

Por isso no `atualizar` a implementação busca a entidade existente e a modifica, em vez
de criar uma nova com o id preenchido — a entidade que já está no contexto de persistência
é a que o Hibernate sabe atualizar.

### Conceito 5 — `@Transactional`

```java
@Transactional
public NinjaResponseDTO atualizar(Long id, NinjaRequestDTO dto) {
    NinjaModel existente = buscarPorIdOuFalhar(id);   // SELECT
    existente.setNome(dto.nome());
    // ...
    return NinjaMapper.toResponseDTO(ninjaRepository.save(existente));  // UPDATE
}
```

São **duas** operações de banco. Sem `@Transactional`, cada uma roda na sua própria
transação: se o `save` explodesse, o banco ficaria com o registro meio alterado. Com
`@Transactional`, as duas rodam na **mesma transação** — se a segunda falhar, a primeira
é desfeita (rollback).

> `save()` já vem com `@Transactional` no `SimpleJpaRepository`. Mas os métodos que você
> **escreve** e que combinam várias operações precisam da anotação explícita.

### Conceito 6 — Query derivada

Adicionadas ao `NinjaRepository` para suportar a regra "email único":

```java
Optional<NinjaModel> findByEmail(String email);
boolean existsByEmail(String email);
boolean existsByEmailAndIdNot(String email, Long id);
```

O Spring Data **lê o nome do método** e monta o SQL:

```
existsByEmailAndIdNot  ->  SELECT COUNT(*) FROM tb_cadastro WHERE email = ? AND id <> ?
```

O parser divide em: `exists` (projeção) + `By` + condição.

**Condições comuns:** `And`, `Or`, `Not`, `Like`, `Containing`, `StartingWith`,
`Between`, `GreaterThan`, `LessThan`, `In`, `OrderBy`...

Quando não dá para deduzir, escreva o JPQL:

```java
@Query("SELECT n FROM NinjaModel n WHERE n.idade > :idade")
List<NinjaModel> findPorIdadeMaiorQue(@Param("idade") int idade);
```

> Cuidado: é **JPQL** (nomes de campo/entidade Java), **não SQL** (nomes de coluna/tabela).
> `NinjaModel`, `idade` — não `tb_cadastro`, `idade`.

### Validação em duas camadas

| | Onde | Tipo | Como falha |
|---|---|---|---|
| `@NotBlank`, `@Email`, `@Min` | DTO | Formato | HTTP 400 automático, mensagem por campo |
| Email único, idade mínima | Service | Regra de negócio | Exceção → 400/409 |

**Não é duplicata.** O DTO protege a *entrada HTTP*. O Service garante a invariante do
domínio **independente de quem chamou** — a API, um teste unitário, um job agendado,
um consumer de fila.

### Ajuste no `MissoesModel`

O `MissoesModel` não tinha Lombok (o `NinjaModel` tinha). Além de `@Data`, foi preciso:

```java
@EqualsAndHashCode(of = "id")
@ToString.Exclude   // no campo List<NinjaModel> ninjas
```

**Por quê?** O `@Data` gera um `equals()` que compara **todos** os campos, incluindo a
lista `ninjas`. E `ninjas` contém `NinjaModel`, que tem o campo `missoes`, que é o
`MissoesModel` que estamos comparando...

> **Recursão infinita** ao comparar dois ninjas que compartilham a mesma missão:
> `ninja → missoes → ninjas → ninja → missoes → ...`

A correção padrão em entidades JPA é comparar **só pela chave primária**, porque no
banco a identidade do registro é o `id`. O `@ToString.Exclude` evita o mesmo problema
no `toString()` (usado em logs e no stack trace das exceções).

## 6. Etapa 3 — DTO e Mapper

### O problema

O Controller devolvendo a entidade crua produzia:

```json
{
  "id": 1, "nome": "Naruto", "email": "naruto@konoha.com", "idade": 17,
  "missoes": {
    "id": 1, "nomeDaMissao": "Proteger Konoha", "dificuldadeMissao": "DIFICIL",
    "ninjas": [                      // ← volta pro ninja...
      { "id": 1, "missoes": { "id": 1, ... } }   // ← ...que tem missoes...que tem ninjas...
    ]
  }
}
```

Não é "JSON grande". É o Jackson seguindo getters até o ciclo fechar.

### A demonstração (ao vivo)

Foi criado um controller temporário que devolvia a entidade crua, e o resultado real foi:

```
GET /debug/entidades   →  HTTP 500
GET /debug/dtos         →  HTTP 200
```

O log do SQL mostrou a sequência exata:

```
INSERT INTO tb_cadastro ...                    ← gravou o ninja
SELECT ... FROM tb_cadastro                    ← findAll()
SELECT ... FROM tb_missoes WHERE id=?           ← a missão foi carregada EAGER
ERROR: Cannot lazily initialize collection of role
       'MissoesModel.ninjas' with key '1' (no session)
```

### Sobre `LazyInitializationException` vs `StackOverflowError`

São **dois sintomas da mesma causa raiz**: expor entidade com relação bidirecional.

- Com `open-in-view=false` (o caso deste projeto): o Jackson chega em `missoes.ninjas`
  (LAZY) e tenta inicializar a coleção, mas a sessão **já foi fechada** →
  `LazyInitializationException`.
- Com `open-in-view=true` (padrão do Spring): a sessão ficaria aberta, a coleção
  carregaria, e aí sim viria o **`StackOverflowError`** (`ninja → missoes → ninjas → ...`).

O `open-in-view=false` não resolveu o problema — apenas mudou *qual* erro aparece.

> A correção "rápida" seria `@JsonIgnore` no campo `ninjas`. Funciona, mas amarra a
> entidade ao formato do JSON. O DTO resolve pela raiz: a entidade não é exposta.

### O código

**DTO de request** (`NinjaRequestDTO.java`):

```java
public record NinjaRequestDTO(
        @NotBlank(message = "Nome é obrigatório")
        String nome,

        @NotBlank(message = "Email é obrigatório")
        @Email(message = "Email inválido")
        String email,

        @Min(value = 16, message = "Ninja deve ter ao menos 16 anos")
        int idade,

        Long missaoId) {
}
```

**DTO de response** (`NinjaResponseDTO.java`):

```java
public record NinjaResponseDTO(
        Long id, String nome, String email, int idade, MissoesDTO missoes) {
}
```

**DTO de missão** (`MissoesDTO.java`) — note o que **não** existe:

```java
public record MissoesDTO(Long id, String nomeDaMissao, String dificuldadeMissao) {
}
```

### Conceito 1 — `record`

`record` (Java 16+) cria classe imutável com `equals`, `hashCode`, `toString` e
construtor canônico — tudo de graça. Perfeito para DTO, que é só transporte.

O acesso é pelo **nome do componente**, não por getter:

```java
dto.nome()          // ✅ record
dto.getNome()       // ❌ record
```

Jackson desserializa records nativamente (usa o construtor canônico) — sem
`@JsonCreator` nem `@JsonProperty`.

> Em Java 8/11, o equivalente é uma classe com Lombok `@Data` + `@NoArgsConstructor` +
> `@AllArgsConstructor`.

### Conceito 2 — Por que dois DTOs

| | `NinjaRequestDTO` | `NinjaResponseDTO` |
|---|---|---|
| Usado em | POST, PUT | GET, POST, PUT |
| Tem `id`? | **Não** | Sim |
| Missão | `missaoId` (Long) | `missoes` (MissoesDTO) |
| Validação? | Sim | Não |

**Por que o request não tem `id`?** Quem escolhe o id é o banco. Se o cliente mandasse
`id`, ele poderia sobrescrever o registro de outro ninja com um PUT. Sem `id` no request,
o id vem **sempre da URL**.

**Por que `missaoId` e não o objeto missão?** Se o request aceitasse a missão inteira, o
cliente poderia mandar `{"id": 99, "nomeDaMissao": "..."}` e sobrescrever a missão 99 — que
pertence a outros ninjas. Mandando só o `missaoId`, o cliente só pode *referenciar* uma
missão existente, nunca *criar ou alterar* uma.

### Conceito 3 — O Mapper

```java
public final class NinjaMapper {

    private NinjaMapper() { }   // classe utilitária: não instanciável

    public static NinjaResponseDTO toResponseDTO(NinjaModel model) {
        if (model == null) return null;
        return new NinjaResponseDTO(
                model.getId(), model.getNome(), model.getEmail(), model.getIdade(),
                toMissoesDTO(model.getMissoes()));
    }

    public static List<NinjaResponseDTO> toResponseDTOList(List<NinjaModel> models) {
        return models.stream().map(NinjaMapper::toResponseDTO).toList();
    }

    public static NinjaModel toModel(NinjaRequestDTO dto) {
        NinjaModel model = new NinjaModel();
        model.setNome(dto.nome());
        model.setEmail(dto.email());
        model.setIdade(dto.idade());
        return model;   // a missão NÃO é setada aqui
    }
}
```

A missão é resolvida depois, pelo Service, a partir do `missaoId`:

```java
private MissoesModel resolverMissao(Long missaoId) {
    if (missaoId == null) return null;
    return missoesRepository.findById(missaoId)
            .orElseThrow(() -> new MissoesNotFoundException(
                    "Missão com id " + missaoId + " não encontrada"));
}
```

> Em projetos maiores usa-se **MapStruct**, que gera esse código por *annotation
> processing* — mesma ideia, zero boilerplate.

### Por que o DTO existe (o quadro completo)

| Problema | Como o DTO resolve |
|---|---|
| Serialização recursiva | Corta o ciclo no grafo de objetos |
| Cliente forjar dados | `missaoId` só referencia, não modifica |
| Vazamento de schema | Adicionar coluna na tabela não vira campo novo na API |
| Cliente mandando `id` no POST | O request DTO não tem `id` |

## 7. Etapa 4 — Controller e tratamento de erros

### O Controller

```java
@RestController
@RequestMapping("/api/ninjas")
public class NinjaController {

    private final NinjaService ninjaService;

    public NinjaController(NinjaService ninjaService) {
        this.ninjaService = ninjaService;
    }

    @GetMapping
    public List<NinjaResponseDTO> listarTodos() {
        return ninjaService.listarTodos();
    }

    @GetMapping("/{id}")
    public NinjaResponseDTO buscarPorId(@PathVariable Long id) {
        return ninjaService.buscarPorId(id);
    }

    @PostMapping
    public ResponseEntity<NinjaResponseDTO> criar(@RequestBody @Valid NinjaRequestDTO dto) {
        NinjaResponseDTO criado = ninjaService.salvar(dto);
        return ResponseEntity.created(URI.create("/api/ninjas/" + criado.id())).body(criado);
    }

    @PutMapping("/{id}")
    public NinjaResponseDTO atualizar(@PathVariable Long id,
                                      @RequestBody @Valid NinjaRequestDTO dto) {
        return ninjaService.atualizar(id, dto);
    }

    @DeleteMapping("/{id}")
    public ResponseEntity<Void> deletar(@PathVariable Long id) {
        ninjaService.deletar(id);
        return ResponseEntity.noContent().build();
    }
}
```

**Repare que não existe import de `NinjaModel` aqui.** Isso é proposital: o Controller
não conhece entidade.

### Conceito 1 — `@RestController` e prefixo de classe

`@RestController` = `@Controller` + `@ResponseBody`. Com `@Controller` (Spring MVC
antigo), o retorno é tratado como **nome de uma view** para o Thymeleaf resolver. Com
`@ResponseBody`, é serializado direto em JSON.

O `@RequestMapping` no nível de **classe** é prefixo — `@GetMapping("/{id}")` vira
`GET /api/ninjas/{id}`. Dá para combinar prefixo com sub-rotas
(`/api/ninjas/{id}/missoes`), útil quando a API cresce.

### Conceito 2 — `@PathVariable` vs `@RequestParam`

| Anotação | De onde vem o valor | Exemplo |
|---|---|---|
| `@PathVariable` | Do **caminho** da URL | `/api/ninjas/{id}` |
| `@RequestParam` | Da **query string** | `/api/ninjas?email=...` |

A conversão `String → Long` é automática. Se mandarem `/api/ninjas/abc`, o Spring
devolve **400** sozinho, antes do seu código rodar.

### Conceito 3 — `@RequestBody` + `@Valid`

```java
public ResponseEntity<NinjaResponseDTO> criar(@RequestBody @Valid NinjaRequestDTO dto) {
```

Dois passos independentes, em ordem:

1. `@RequestBody` → o Jackson lê o corpo JSON e **constrói** o `NinjaRequestDTO`
   (usando o construtor canônico do record)
2. `@Valid` → o Spring roda as validações declaradas no DTO

**Se o `@Valid` reprovar, o método do Controller nem executa.** A exceção
(`MethodArgumentNotValidException`) é capturada pelo handler global e vira 400 com o mapa
por campo.

> Sem `@Valid`, o `@NotBlank` é só decoração — nada acontece.

### Conceito 4 — `ResponseEntity` e status codes

Sem `ResponseEntity`, o Spring infere o status (retorno de `void` → 200, qualquer outro →
200). Para CRUD real é preciso controle explícito:

```java
ResponseEntity.created(URI.create("/api/ninjas/" + criado.id())).body(criado);  // 201 + Location
ResponseEntity.noContent().build();                                                // 204
ResponseEntity.status(HttpStatus.NOT_FOUND).body(erro);                           // 404
```

O **201 + header `Location`** não é decoração: o `Location` diz ao cliente **qual é a URL
do recurso que acabou de ser criado**. É o contrato do HTTP.

| Código | Quando |
|---|---|
| 200 | GET, PUT — tem conteúdo de volta |
| 201 | POST — recurso criado (com `Location`) |
| 204 | DELETE — sucesso, sem corpo |
| 400 | entrada inválida (validação / regra de negócio) |
| 404 | recurso não existe |
| 409 | conflito (recurso já existe) |
| 500 | erro inesperado |

> **Melhoria pendente:** email duplicado está retornando 400, mas o código semanticamente
> mais correto seria **409 Conflict** — a requisição é válida, mas conflita com o estado
> atual. Basta criar uma `EmailJaExisteException` e mapear para 409 no handler.

### Conceito 5 — `@RestControllerAdvice`: a peça que fecha o ciclo

Antes do advice, o Spring tratava `NinjaNotFoundException` como erro genérico:

```json
{"timestamp":"...","status":500,"error":"Internal Server Error","path":"/api/ninjas/999"}
```

Com o advice:

```json
{"timestamp":"...","status":404,"erro":"Not Found",
 "mensagem":"Ninja com id 999 não encontrado",
 "caminho":"/api/ninjas/999","campos":{}}
```

**Por que o tradutor fica fora do Service?**

Porque o Service não deveria saber sobre HTTP. Ele lança `NinjaNotFoundException` — uma
**verdade de domínio** ("esse ninja não existe"). Quem traduz "não encontrado" em 404 é
o advice.

É o mesmo princípio do DTO: **cada camada conhece apenas a próxima**. Se amanhã a mesma
regra for usada por um consumer de Kafka ou um job agendado, a `NinjaNotFoundException`
continua válida — só o tradutor HTTP muda (ou não existe).

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(NinjaNotFoundException.class)
    public ResponseEntity<ErroResponse> ninjaNaoEncontrado(NinjaNotFoundException ex,
            HttpServletRequest request) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND)
                .body(ErroResponse.de(HttpStatus.NOT_FOUND, ex.getMessage(),
                        request.getRequestURI()));
    }

    @ExceptionHandler(MissoesNotFoundException.class) { /* ... 404 ... */ }

    @ExceptionHandler(IllegalArgumentException.class) { /* ... 400 ... */ }

    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErroResponse> validacaoFalhou(MethodArgumentNotValidException ex,
            HttpServletRequest request) {
        Map<String, String> campos = new LinkedHashMap<>();
        ex.getBindingResult().getFieldErrors()
                .forEach(erro -> campos.putIfAbsent(erro.getField(), erro.getDefaultMessage()));
        return ResponseEntity.badRequest()
                .body(ErroResponse.de(HttpStatus.BAD_REQUEST, "Dados inválidos",
                        request.getRequestURI(), campos));
    }

    @ExceptionHandler(Exception.class)
    public ResponseEntity<ErroResponse> erroInesperado(Exception ex,
            HttpServletRequest request) {
        log.error("Erro inesperado em {} {}", request.getMethod(), request.getRequestURI(), ex);
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR)
                .body(ErroResponse.de(HttpStatus.INTERNAL_SERVER_ERROR,
                        "Erro interno inesperado", request.getRequestURI()));
    }
}
```

O `@ExceptionHandler` é o mesmo mecanismo do `@GetMapping`/`@PostMapping`, mas para
exceções: "quando acontecer X, execute este código". O Spring escolhe o handler pelo
**tipo mais específico** da exceção — por isso `NinjaNotFoundException` (específica) ganha
do `Exception` (genérica).

O handler genérico de `Exception` existe por segurança: devolve 500 com mensagem genérica
e registra o stack trace completo no log. Sem ele, a página de erro padrão do Boot poderia
vazar detalhes internos.

> **Alternativa moderna:** o `ProblemDetail` do Spring Framework 6+ (RFC 9457), que o
> Spring serializa automaticamente como `application/problem+json`:
> ```java
> ProblemDetail pd = ProblemDetail.forStatusAndDetail(HttpStatus.NOT_FOUND, ex.getMessage());
> pd.setTitle("Ninja não encontrado");
> return pd;
> ```

## 8. Armadilhas encontradas

### 8.1 `ClassNotFoundException` — `NinjaModel` (antes da jornada)

**Causa:** a classe não estava no diretório correspondente ao seu `package`.

**Regra:** o Java compila por estrutura de pastas. `package com.example.demo.Ninjas;`
exige o arquivo em `src/main/java/com/example/demo/Ninjas/NinjaModel.java`.

### 8.2 `LazyInitializationException` / `StackOverflowError` na serialização

**Causa:** entidade com relação bidirecional exposta direto no JSON.

**Sintoma A** (com `open-in-view=false`): `Cannot lazily initialize collection of role
'MissoesModel.ninjas' (no session)`.

**Sintoma B** (com `open-in-view=true`): `StackOverflowError` por recursão infinita.

**Solução:** DTO. A entidade não atravessa a fronteira do Service.

### 8.3 Recursão infinita no `equals()` (Lombok + JPA)

**Causa:** `@Data` gera `equals()` comparando todos os campos, incluindo a lista `ninjas`
→ `ninja → missoes → ninjas → ninja → ...`

**Solução:** `@EqualsAndHashCode(of = "id")` nas entidades (a identidade no banco é o id)
e `@ToString.Exclude` na coleção.

### 8.4 `NoClassDefFoundError` no `./mvnw test`

**Causa:** o plugin Surefire estava baixado pela metade no `~/.m2` local. Rodar com `-o`
(offline) impedia a correção.

**Solução:** rodar `./mvnw test` **sem** `-o` uma vez, para o Maven completar o download.
Depois, `-o` volta a funcionar.

### 8.5 `MissoesModel` sem Lombok

**Causa:** `@Data` ausente, então não havia getters/setters para o Service.

**Solução:** adicionar `@Data` + `@NoArgsConstructor` — junto com as proteções de
`equals`/`toString` do item 8.3.

### 8.6 `@RequestMapping` vazio no Controller

**Causa:** `@RequestMapping` sem valor no nível de classe, o que não faz nada.

**Solução:** `@RequestMapping("/api/ninjas")` como prefixo, e o `/boasvindas` movido
para um `HomeController` próprio.

## 9. Glossário de anotações

### Spring / IoC

| Anotação | Onde | O que faz |
|---|---|---|
| `@SpringBootApplication` | classe main | Ativa auto-configuração + component scan a partir do pacote da classe |
| `@Component` | qualquer classe | Marca como bean do container |
| `@Service` | classe de negócio | `@Component` com estereótipo de "camada de negócio" |
| `@Repository` | classe de persistência | `@Component` com estereótipo de "acesso a dados" |
| `@Controller` / `@RestController` | classe web | Trata requisições HTTP (`@RestController` = `+ @ResponseBody`) |
| `@RestControllerAdvice` | classe global | Aplica handlers de exceção a todos os controllers |
| `@Configuration` | classe de config | Declara beans (evita quando possível) |
| `@Bean` | método | Produz um bean gerenciado pelo container |

### Persistência (JPA/Hibernate)

| Anotação | O que faz |
|---|---|
| `@Entity` | Marca a classe como entidade (vira tabela) |
| `@Table(name = "...")` | Define o nome da tabela |
| `@Id` | Marca a chave primária |
| `@GeneratedValue(strategy = IDENTITY)` | Auto-increment do banco |
| `@Column(name = "...")` | Define o nome da coluna |
| `@OneToOne` / `@OneToMany` / `@ManyToOne` / `@ManyToMany` | Cardinalidade do relacionamento |
| `@JoinColumn(name = "...")` | Define a coluna da FK |
| `@mappedBy = "..."` | Lado inverso da relação (aponta para quem tem a FK) |
| `@Enumerated(EnumType.STRING)` | Persiste enum como texto (não como número) |
| `@CreationTimestamp` / `@UpdateTimestamp` | Preenchimento automático de datas |

### Web

| Anotação | O que faz |
|---|---|
| `@RequestMapping` | Mapeia rota (prefixo de classe ou método) |
| `@GetMapping` / `@PostMapping` / `@PutMapping` / `@DeleteMapping` / `@PatchMapping` | Atalhos por verbo HTTP |
| `@PathVariable` | Valor vindo do caminho da URL (`{id}`) |
| `@RequestParam` | Valor vindo da query string |
| `@RequestBody` | Desserializa o corpo JSON num objeto |
| `@Valid` | Dispara as validações declaradas no objeto |
| `@ResponseStatus` | Fixa o status code de retorno |
| `@ExceptionHandler` | Trata uma exceção específica |

### Validação (Jakarta Bean Validation)

| Anotação | Regra |
|---|---|
| `@NotNull` | Não pode ser `null` |
| `@NotBlank` | Não pode ser `null`, vazio ou só espaços |
| `@NotEmpty` | Não pode ser `null` ou vazio (listas/strings) |
| `@Email` | Formato de email |
| `@Min` / `@Max` | Limite mínimo / máximo |
| `@Size(min, max)` | Tamanho de string ou coleção |
| `@Pattern(regexp = "...")` | Expressão regular |

## Resumo das decisões de arquitetura

| Decisão | Motivo |
|---|---|
| Entidade nunca sai do Service | Evita serialização recursiva e vazamento do schema |
| DTO separado para request e response | Impede o cliente de forjar `id` ou modificar dados de terceiros |
| Injeção por construtor com `final` | Objeto nasce completo; dependência imutável |
| Exceções de domínio no Service | O Service não sabe sobre HTTP |
| `@RestControllerAdvice` traduz para HTTP | Cada camada conhece só a de baixo |
| Validação de formato no DTO, regra no Service | Falha rápido na borda + invariante garantida no domínio |
| `@Transactional` em métodos multi-operação | Atomicidade e rollback |
| `open-in-view=false` | Fecha a sessão no fim da requisição; evita N+1 e conexões ociosas |
| `@EqualsAndHashCode(of = "id")` | Identidade de entidade JPA é a chave primária |
